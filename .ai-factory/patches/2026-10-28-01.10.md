# Guard писал URL с query-строкой в лог; подделка молча принимала неверный slug и повтор участника

**Date:** 2026-10-28 01:10
**Files:** src/nest/permission.guard.ts, src/testing/fake-platform.ts, CHANGELOG.md, test/unit/permission-guard.spec.ts, test/unit/fake-platform.spec.ts
**Severity:** medium

## Problem

1. Логи `error` («VerdeectAuthGuard не найден в DI») и `debug` («no Principal, calling VerdeectAuthGuard») в `PermissionGuard` содержали `{ route: request.url }`. URL с query-строкой (`/p/one?token=secret`) целиком попадал в лог.
2. `createFakePlatform`:
   - из `tenantId` вида `_acme` или `''` выводил slug `-acme` или `''`, который не проходит схему Platform; конверт `policyChanged` молча получался невалидным;
   - повтор `(tenantId, sub)` в `members` давал смешанного участника: `memberId` брался из первой записи, `permissions` — из последней.

## Root Cause

1. План задал «лог с путём маршрута», и при реализации взят первый доступный `request.url`. Не учтено, что это полный URL запроса, а не шаблон маршрута, а значит в лог попадают пользовательские данные из query.
2. Правило slug в PRD v1.10 описывало только нормализацию и не говорило, что делать с результатом, который шаблону не отвечает. Код повторил правило дословно и ничего не проверил. Для `members` проверки повторов не было: `member()` переиспользует уже заведённое состояние, то есть повтор считался обращением к существующему участнику, а не ошибкой входных данных.

## Solution

1. Guard пишет `{ handler: '<Class>.<method>' }` (`context.getClass().name` и `context.getHandler().name`); URL в логи не попадает. Тест: запрос `?token=secret` → в записях guard только `handler`, во всех логах нет `secret` и `?token`.
2. По PRD v1.11:
   - slug из `tenantId` проверяется шаблоном Platform; если не проходит — `TypeError` с подсказкой задать `companies[].tenant`;
   - явный `tenant` проверяется до вывода slug, поэтому `{tenantId: '_acme', tenant: '_acme'}` допустим;
   - повтор `(tenantId, sub)` в `members` → `TypeError` с полем `members`.
   - TSDoc и CHANGELOG обновлены.

## Prevention

- В лог — идентификатор кода (класс и обработчик, шаблон маршрута), а не данные запроса (URL, query, тело).
- Нормализация значения, которое уходит во внешний контракт, должна заканчиваться проверкой этого контракта. Молчаливо «исправленное» значение хуже ошибки.
- Для входных списков, где ключ должен быть уникальным, — явная проверка повторов с `TypeError` при создании.
