# Project Rules for /aif-plan

> Bundle: aif-prompts 2026-10-13 (portable baseline; /aif-evolve may extend it).
> Last updated: 2026-10-30
> Based on: 94 analyzed patches + 16 aif-improve fix logs + manual rules

## Rules

### Requirements Package Authority
**Source**: manual, 2026-10-05
**Rule**: When the request references a requirements package `requirements/<NNNN>-<slug>/`, its `feature.md` (or `prd.md`) is the highest-authority behavioral source — above ROADMAP.md and DESCRIPTION.md. Files in `mockups/` refine UI only; `files/` is reference material. Declare this hierarchy in `## Requirements Reconciliation`. Every task description MUST cite the requirement IDs it implements (FR-, BR-, EC-, AC-). Items marked `[OPEN]` are unresolved questions: ask the user (or record a blocking open question in ultra) — never silently assume an answer. Items marked `[ASSUMPTION]` may be used but must be listed in Requirements Reconciliation. If the package declares `Изменяет:` (changes) earlier package IDs, include tasks that replace the old behavior and update its tests.

### Milestone Scope
**Source**: manual, 2026-10-05
**Rule**: When the request names a roadmap milestone (`E{n} {Name}`) and a scope (`Скоуп этапа: UC-…, AC-…`), the plan covers **only** the requirement IDs of that scope plus the FR/BR/EC attached to its UCs. Write the scope as a list of IDs in `## Requirements Reconciliation` under `Milestone scope`. Requirements of the same package assigned to other milestones (see the package `README.md`, section «Этапы») are out of scope — do not plan them, and do not report them as gaps. Code delivered by earlier milestones is existing code: extend it, do not rebuild it. If the request names no scope, the whole package is in scope.

### Roadmap Linkage Is Expected
**Source**: manual, 2026-10-05
**Rule**: If `.ai-factory/ROADMAP.md` exists and the request names a milestone, propose linkage to that exact milestone first and write `## Roadmap Linkage` with its name. Skipping linkage is acceptable only for `fast` plans that implement no requirement IDs.

### Consult Specialist Before Decomposition
**Source**: manual, 2026-10-05
**Rule**: Before writing tasks, read the stack specialist skill(s) in REFERENCE mode and follow their architecture, Type Placement / layering rules, naming conventions and Skill Interaction Patterns (creation order). **Laravel backend** → `/laravel-specialist`. **Vue SPA (`resources/js/`)** → `/laravel-vue-specialist`. **Python** → `/python-specialist`. **NestJS backend (TypeScript, `src/modules/`)** → `/nestjs-specialist`. Do not invent alternative folder structures.

### Every File Task Names Its Code Skill
**Source**: manual, 2026-03-30 / 2026-10-05
**Rule**: Every task that creates or modifies a source file MUST contain a `**Skill:**` field with the exact code-generation skill and mode, e.g. `**Skill:** laravel-code-service-http-controller (CREATE)`. Pick the skill via the specialist's routing table and decision trees: `laravel-code-*` (fallback `create-php-file`), `laravel-vue-code-*` (fallback `create-vue-file` / `create-ts-file`), `python-code-*`, `nestjs-code <type> <module> [service] <Name>` for NestJS (e.g. `**Skill:** nestjs-code use-case platform members InviteMember (CREATE)`). One task = one primary file type = one skill. Tasks that only delete files, run commands or edit non-code config may omit the field.

### Flat Module Skill Arguments
**Source**: manual, 2026-03-30 / 2026-10-13 (replaces "Flat Module Skill Arguments (Laravel)")
**Rule**: When generating the `**Skill:**` field for a Laravel task, determine the module structure from `ARCHITECTURE.md` / `app/Modules/{Module}/CLAUDE.md` or by checking whether `{Service}Service/` directories exist in the module. For **flat modules**, omit the Service argument — pass only Module and ComponentName. For **service-based modules**, pass Module, Service and ComponentName. Example flat: `Skill: laravel-code-service-business-action Organization CreateOrgAction (CREATE)`. Example service-based: `Skill: laravel-code-service-business-action App Provisioning RetryAction (CREATE)`. **NestJS:** the module is service-based when `src/modules/{module}/` contains `{name}-service/` directories (see `src/modules/{module}/CLAUDE.md`); flat → `nestjs-code action billing InsertInvoice (CREATE)`, service-based → `nestjs-code action platform members InsertMember (CREATE)`.

### Consult Side-Effects Checklist
**Source**: 2026-03-05-10.30.md, manual 2026-03-30 / 2026-10-05
**Rule**: During Step 3 (Explore Codebase), for every task consult the specialist's Side-Effects Checklist and add each cascading change as its own task. **Laravel:** new role/permission → update Policy methods + add Factory state; middleware changed on routes → update Policies for newly admitted roles; tests with specific roles → verify Factory has matching state; backend access rules changed → mirror in frontend route guards. **Vue SPA:** new view → route entry (+ auth guard if protected); new API endpoint → TypeScript types + API module method; new store → verify API service exists; auth flow changed → router guards, auth store, API interceptors. **Python:** new model → register in `alembic/env.py` + migration task; new module → `pyproject.toml` script entry + alembic registration; config field → `.env.example` + aggregated config; new service → wire into pipeline steps; migration → verify `down_revision` chain. **NestJS:** new table → Drizzle schema + generated SQL migration + RLS policy on `tenant_id` + `FORCE ROW LEVEL SECURITY` + tenant index + tenant-isolation test; new permission → Platform permission catalog + `@Permission()` + 403 test; new route → zod request/response schemas + OpenAPI + 401/403/422 tests; new outgoing event → schema in `@verdict/contracts` + event catalog entry + "outbox row in the same transaction" test; new consumer → queue binding + DLQ + redelivery (inbox) test; new env key → `env.schema.ts` + `.env.example` + compose files; `I*Service` contract change → every implementation and test double; new module/service → registration in the parent module + documentation.

### Documentation Regeneration Tasks
**Source**: manual, 2026-10-05
**Rule**: Add closing tasks that regenerate CLAUDE.md documentation for every touched module/service/directory, strictly bottom-up, with the generator the specialist prescribes. **Laravel:** flat module → `laravel-generate-module-documentation` (Level 2); service-based → `laravel-generate-service-documentation` (Level 3) then module (Level 2); module created/removed → also `laravel-generate-global-modules-documentation`. **Vue:** `laravel-vue-generate-directory-documentation` then `laravel-vue-generate-global-documentation` if structure changed. **Python:** `python-generate-module-documentation` then `python-generate-global-documentation` if a module was created/removed. **NestJS:** `nestjs-generate-documentation service` (Level 3, service-based modules only) then `nestjs-generate-documentation module` (Level 2), plus `nestjs-generate-documentation global` when a module was created/removed. Never use Level 3 for flat modules; never use one stack's generators for another stack.

### Validate Tasks Against Specialist Plan Review Checklist
**Source**: manual, 2026-03-30
**Rule**: After drafting all tasks and BEFORE writing the plan file, run the task list through the **Plan Review Checklist** of each relevant specialist (`/laravel-specialist`, `/laravel-vue-specialist`, `/python-specialist`, `/nestjs-specialist`) — component type vs decision tree, naming, skill routing, creation order, side-effects, documentation level, cross-module access, FK chains, event payloads, provider ordering, vendor:publish conflicts. Fix all flagged issues before saving the plan. Domain-specific rules live in the specialists' checklists, not here.

### Architectural Deviation Justification
**Source**: 2026-03-05-16.20.md, manual 2026-03-30
**Rule**: When a task creates a component that deviates from the specialist decision tree, the task description MUST include an "Architectural deviation" note with: (1) which decision-tree rule is deviated from, (2) at least 2 concrete reasons, (3) explicit acknowledgment that this is a conscious decision. Without it `/aif-improve` flags the task as SKILL-002. Examples: **Laravel** — Business Controller without DB writes, Action with external side effects, read-only method in a write service. **Vue** — component with direct API calls instead of a store, view without route registration, composable with side effects. **Python** — repository with business logic, service accessing the DB bypassing the repository, service calling another service instead of the pipeline coordinating them. **NestJS** — action that opens a transaction or writes the outbox, HTTP controller with several routes, tenant table without RLS (`// global:`), consumer without inbox idempotency.

### Check Shared Infrastructure for Cross-Plan Duplicates
**Source**: 2026-03-07-aif-improve-analysis.md
**Rule**: Before adding a shared infrastructure component (queue constant in `Shared/Queues.php`, shared enum, config key, shared type; in NestJS — anything in `src/shared/*` or the `@verdict/*` packages), check: (1) does it already exist in the codebase? (2) does another plan of the same feature decomposition already add it? If yes — reference the existing component or the other plan's task instead of creating a duplicate, and note it in the task (e.g. "ALERTING queue constant — created in Plan 5.3, Task 5a").

### Post-Planning Verification via `/aif-improve`
**Source**: 2026-03-04-18.30.md, manual 2026-10-05
**Rule**: After saving the plan (Step 5) and BEFORE presenting Next Steps (Step 6), invoke `/aif-improve` on the saved plan artifact (pass its path with `@`). Apply returned fixes in place and re-run until no fixes are found, **at most 3 passes**; if issues remain after 3 passes, list them in the final report instead of looping further. Report the result before Step 6.

### Mandatory Test Phases
**Source**: manual, 2026-10-05
**Rule**: Regardless of the "Tests?" answer, every plan for a requirements package MUST contain: (1) **server tests** — unit tests for pure logic and feature tests for every HTTP/Inertia endpoint, including role access (401/403 and hidden write actions), validation (422) and the error flows of each UC; database-engine-specific constraints in their own group (e.g. `pgsql`); one test per AC with the AC ID in its name. Framework follows the project: **Laravel** — `Skill: laravel-code-test`, which detects Pest (`pestphp/pest` in composer.json) or PHPUnit; **Python** — pytest as the python specialist prescribes; **NestJS** — Vitest via `Skill: nestjs-code test <unit|integration|http> …`: `unit` (`*.spec.ts`) for domain and actions, `integration` (`test/integration/*.int-spec.ts`, real PostgreSQL/RabbitMQ through Testcontainers, application DB role) for repositories, use-cases, RLS tenant isolation, outbox atomicity and consumer redelivery, `http` (`test/http/*.http-spec.ts`, Supertest) for every route — 401/403/422/409 and success; (2) **browser tests** — when the package has a UI: one Playwright spec per UC (main + alternative + error flows), AC IDs in test titles (`Skill: laravel-vue-code-e2e`); (3) **e2e data** — tasks that extend the E2E seeder profiles and/or the `/__testing__/fixtures/{name}` registry for every state the scenarios need (empty states use a dedicated seeder profile and `*.serial.spec.ts`); (4) **stable selectors** — UI tasks list the `data-testid` attributes the scenarios rely on (roles/labels first, `data-testid` for structural elements without an accessible name). Test tasks are placed after the code they cover and before documentation tasks.

### Traceability Section
**Source**: manual, 2026-10-05
**Rule**: The plan entrypoint MUST contain `## Traceability` — a table `UC/AC → task(s) → test file / test title`. Every AC and UC **in the plan's scope** (milestone scope, or the whole package when no scope is declared) appears in it; an in-scope AC without a test task is a planning error.

### E2E Infrastructure Check
**Source**: manual, 2026-10-05
**Rule**: Before planning browser tests, verify the e2e contour exists: `compose.e2e.yml`, Makefile targets `e2e-up`/`e2e-reset`/`test-browser`, `tests/Browser/fixtures.ts` with role pages, testing routes gated by `E2E_TESTING_ROUTES`. If any part is missing, add a first phase "E2E infrastructure" (via `/aif-dockerize` + `/aif-build-automation` rules and `laravel-vue-code-e2e` for fixtures) instead of improvising per-feature setups. **NestJS backend services without UI** have no browser contour: verify instead `vitest.config.ts` + `vitest.integration.config.ts`, the Testcontainers helpers in `test/support/`, and Makefile targets `test` / `test-integration`; if missing, add a first phase "Test infrastructure".

### Error Tracking (GlitchTip)
**Source**: manual, 2026-10-12
**Rule**: Production errors go to the self-hosted GlitchTip (`https://errors.ppmk.pro`, Sentry SDKs, policy and templates in the local skill `glitchtip-integration`). (1) If the project has no integration yet (no `sentry/sentry-laravel` / `@sentry/vue` / `sentry-sdk` / `@sentry/nestjs`), the first plan of an INIT or the next milestone adds an "Error tracking" phase: backend SDK, frontend SDK with runtime DSN, source maps upload in the CI build, production variables, empty DSN in dev/e2e/tests, scrubber and user-ID tests — each file task with its code skill and `glitchtip-integration` named as the integration reference. (2) Every task that adds an entry point (queue consumer, scheduled or console command, websocket handler, external callback, Python CLI/pipeline step) states how its errors reach GlitchTip; a `catch` that continues work calls `report($e)` / `capture_exception` / `Sentry.captureException(error)` (NestJS: RabbitMQ consumers, `@Cron` jobs and the outbox relay are entry points). (3) Never plan tracing, replay or profiling (errors only).

### Fast Test Suites
**Source**: manual, 2026-10-30 (verdeect-identity, ID-13–ID-16)
**Rule**: Plans that create or extend test infrastructure (the foundation milestone, a new integration suite, a new e2e contour) build it fast from the start; plans of later milestones follow the same layout:
(1) Password-hashing / KDF cost is configurable; integration tests and the e2e contour use the minimum cost (scrypt `N=1024`, bcrypt rounds 4, minimal argon2), except tests that verify the production hash format or cost and the timing / load suites, which pin production values. Production compose and `.env.example` never set the test value.
(2) Containers (database, broker, cache, mail catcher) start once per run in global setup and migrations run once; files clean their own data (truncate, flush, delete their own mails by recipient) instead of restarting containers.
(3) NestJS / Vitest: the integration config has two projects — `shared` with `isolate: false` (the module graph is imported once per worker) and `isolated` with `isolate: true`. A file goes to `isolated` when it writes `process.env` / `vi.stubEnv`, uses `vi.mock`, patches prototypes (`vi.spyOn(X.prototype)`), initialises Sentry or another process-global (undici dispatcher, `globalThis.fetch`), or asserts output of a process-wide singleton (e.g. the nestjs-pino root logger in CLI log assertions). The `isolated` list is explicit in the config with a reason per file; the rule for adding files is in the config comment and in the root agent rules file. Every file closes its applications, pools and connections in `afterAll`; spies on instances are restored. A leak between files is fixed in the test support code, not hidden by moving the file to `isolated`.
(4) Timing-sensitive and load specs live in their own configs and Makefile targets (see the aif-build-automation rule "Test Levels"), never in `test-integration`.
(5) Dependency and version policies (e.g. "no global undici dispatcher ≥ 7 in production dependencies") are static checks in `make analyse` (lockfile / `pnpm why --prod`), not unit tests that boot the application; a runtime assertion, if needed, goes into an existing http spec that already boots it.
(6) Fake timers where elapsed time is not the subject of the test (code expiry, session windows — or shift timestamps in the database); real waits only where the behaviour of a real driver is tested (broker reconnect, connection timeouts, graceful shutdown).

### Browser Tests Without a Vue Stack
**Source**: manual, 2026-10-15
**Rule**: Browser tests are mandatory for every UI stack, not only Laravel + Vue. If the repository contains any browser application (React + Vite pages of a NestJS service, a standalone React SPA, etc.), the exemption "NestJS backend services without UI have no browser contour" does NOT apply: (1) every UC with UI gets one Playwright spec under `tests/Browser/` covering the main, alternative and error flows, AC IDs in test titles, `test.describe('UC-N: …')`; (2) the E2E Infrastructure Check expects the same contour as Laravel + Vue — `compose.e2e.yml`, Makefile targets `e2e-up` / `e2e-reset` / `test-browser`, `playwright.config.ts`, `tests/Browser/fixtures.ts` with role pages, testing routes or fixture endpoints gated by `E2E_TESTING_ROUTES`; if any part is missing, add a first phase "E2E infrastructure" (in an INIT this belongs to the first milestone with UI, which runs after `/aif-dockerize` and `/aif-build-automation` generated the base compose files and Makefile; follow their e2e rules); (3) do NOT reference `Skill: laravel-vue-code-e2e` — it is Laravel/Vue-specific; browser-test tasks state `Skill: none — Playwright, conventions of laravel-vue-code-e2e without Vue/Inertia specifics` and follow those conventions: seeder profiles / fixtures for every state, `*.serial.spec.ts` for empty states, roles and labels first, `data-testid` for structural elements; (4) when the package has mockups in `mockups/`, UI tasks name the mockup files they implement and take layout, spacing and components from them, colours and fonts from the design tokens; canvas service markup is not copied into components.

### Visual Regression Against Mockups
**Source**: manual, 2026-10-21 (verdeect-identity, plan "pixel-perfect pages")
**Rule**: Applies when the requirements package has exported mockups for screens this repository implements (`requirements/*/mockups/**/*.dc.html` or other self-contained HTML artboards; `mockups/reference/` is excluded). Mockups are the visual norm, and pixel comparison is a permanent regression mechanism, not a one-off audit.
(1) Contour — built once: in the first milestone with UI right after the e2e contour; in an existing project without it — as the first phase of the next plan with UI. A separate `playwright.visual.config.ts` (not the e2e config), specs in `tests/Visual/`, Makefile target `test-visual` that runs Playwright inside the pinned image `mcr.microsoft.com/playwright:v<version>-noble` (version equal to `@playwright/test` in package.json, so fonts and rasterization are deterministic), the target is part of `make ci`, and a GitLab CI job `test-visual` without `allow_failure` (it needs no e2e contour because the backend is stubbed).
(2) Baselines are rendered from the mockup HTML itself in the same Chromium at the artboard size with `deviceScaleFactor: 1` (canvas service wrappers removed before the first paint), never taken from the exported PNG and never accepted with `--update-snapshots`; a changed mockup becomes the new baseline automatically.
(3) The page under test runs without the backend: built static assets, every API call stubbed with `page.route` returning exactly the data shown on the artboard, fixed clock, timezone and locale, production security headers (CSP) applied; an unexpected request or a CSP violation fails the test.
(4) Two checks per artboard: a screenshot comparison (`maxDiffPixels: 0`, `threshold` ≤ 0.02 for anti-aliasing noise, animations and caret disabled) and a computed-style probe over a fixed selector list (font, colour, spacing, size, border, radius, shadow) that reports `selector property: mockup → page`.
(5) `tests/Visual/artboards.ts` is the catalog: every artboard → how to reach its state (page kind, stubs, user steps, clock). Guard test: every `*.dc.html` in the implemented mockup folders is in the catalog, so a new mockup without a check fails the run. Mobile artboards `*-Mobile` (390 px wide) are compared the same way at their size. E-mail mockups, if present, are compared against the real template rendered with the artboard data and a fixed `now`.
(6) `tests/Visual/deviations.ts` is the registry of approved deviations (`artboard`, `kind: mask | elements`, `selectors`, `reason`, `source` — a requirement ID or a technical constraint). Empty is the goal; every entry is approved by the user at a ⛔ checkpoint task. Guard tests: every entry has non-empty fields, every mask matches at least one element.
(7) Every plan that touches UI with mockups adds the artboards of its screens to the catalog within that plan, and its LAST implementation task is "Visual check": `make test-visual` green for the whole catalog. Differences are fixed in code (markup, CSS, templates), not with masks, thresholds or edited baselines. If the mockup itself is wrong or contradicts the requirements, the task stops and asks the user: mockups are fixed in the design source and re-exported, plans never edit files under `requirements/`.
(8) `## Traceability` lists artboard → visual test next to UC/AC → test.

### Expected Errors Are Not Reported
**Source**: manual, 2026-10-23 (verdeect-bff, review E1)
**Rule**: In the "Error Tracking (GlitchTip)" phase and in entry-point tasks, plan the split explicitly: unexpected errors → `Sentry.captureException` / `report()` / `capture_exception`; expected errors (known codes of the error table, expected 503/504 of an unavailable dependency, 4xx request errors of the framework, failed health probes) → `warn` log and metrics, no reporting. Plan one HTTP test on a real route proving that a request error is not reported and an unexpected error is reported exactly once.

### Library Package Scope
**Source**: manual, 2026-10-27 (verdeect-platform-client, adapted from verdeect-auth)
**Rule**: This repository is a published npm library, not a service. "E2E Infrastructure Check" and "Error Tracking (GlitchTip)" do not apply: plan no Dockerfile, compose, e2e, Playwright or GlitchTip tasks (a library never reports errors; the consuming service does). Mandatory tests: Vitest unit tests (`Skill: nestjs-code test`) named by AC IDs, the performance set (`vitest.perf.config.ts`), package checks (tarball content, publint, attw), consumer tests that install the packed tarball into `test/consumer`, and — in the milestone that owns them — contract tests (layer C, `test/contract`, Testcontainers against the real `verdeect-platform` image, local only). The Platform contract is fixed by `platform-lite/prd.md` and mirrored in §3 of the requirements: plans never change request/response shapes, decision codes or their messages, or the meaning of `epoch` / `minEpoch` unless the requirements package says so. Files copied from `verdeect-platform` (decision codes, permission and module catalog, event JSON Schemas) carry the source path and commit in a header comment and are re-copied, never edited by hand. A change of the public surface (exports, signatures, error codes, options) needs a task that updates README, TSDoc and `CHANGELOG.md`; a breaking change needs a major version.
